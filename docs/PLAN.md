# HDTreeMap — Plan

A native disk-usage treemap viewer for macOS, Windows and Linux, built on agg-gui.
You point it at a drive or folder, it scans the folder in parallel, and it shows every
file as a shaded rectangle whose area is proportional to the file's size. The goal is
a small, fast and clean tool, not a WinDirStat clone with every feature.

Status: **v0.1.0 complete (2026-10-10): M0–M6 done.** Open items are listed in §6. License MIT. Repo github.com/larsbrubaker/HDTreeMap (rust-apps submodule).

---

## 1. Prior art and what we take from each

| Project | Platform / license | What it does well | What we borrow |
|---|---|---|---|
| **WinDirStat** (KDirStat lineage) | Windows, GPL | Three linked views: directory tree, treemap, extension list. Cushion shading; colour by extension. | The three linked views, cushion shading and the extension legend. |
| **QDirStat** (KDirStat successor) | Linux/Qt, GPL | Same model as WinDirStat, plus "cleanup actions" and handling for mount points and hard links. | Staying on one filesystem, counting hard links once, a small fixed set of actions. |
| **GrandPerspective** | macOS, GPL | One clean treemap window, colours by extension, folder or date, and zoom into a folder. | Zoom in and out with a breadcrumb, a minimal UI, and a choice of colour scheme. |
| **Disk Inventory X** | macOS, GPL | WinDirStat-style layout for the Mac. | Confirms the tree + map + legend layout is what users expect. |
| **SpaceSniffer / WizTree** | Windows, closed source | Very fast. WizTree reads the NTFS MFT directly. SpaceSniffer shows results while it is still scanning. | Speed sets user expectations. Reading the MFT is out of scope for us (it needs admin and only works on Windows). |
| **dua-cli / diskonaut / gdu / ncdu** | Rust and Go TUIs | Parallel walks (dua uses `jwalk`), apparent vs allocated size, inode de-duplication, delete from inside the tool. | Parallel `jwalk` scanning, the size-mode toggle, and inode de-duplication. |
| **Filelight / Baobab** | KDE / GNOME | Sunburst (radial) charts. | Nothing in v1. A sunburst view is a possible later addition. |

Algorithms:
- **Squarified treemap** (Bruls, Huizing, van Wijk, 2000): keeps rectangles close to square, so they are easy to point at and compare.
- **Cushion treemap** (van Wijk and van de Wetering, 1999): per-pixel parabolic shading that makes the folder nesting visible without drawing borders. WinDirStat and QDirStat both use it.

## 2. v1 feature set (small but useful)

**Scanning**
- Start screen lists mounted volumes, each with a used/free bar (via the `sysinfo` crate), plus a **Choose Folder…** button (native picker via `rfd`). A path given on the command line is also accepted.
- Parallel scan with live progress: files and folders counted, bytes so far, current path, elapsed time, and Cancel.
- Size mode: **allocated** ("size on disk", the default) or **apparent**. Switching modes re-lays out the map without rescanning, because both sizes are stored.
- Correctness defaults:
  - Stay on one filesystem.
  - Don't follow symlinks or Windows junctions.
  - Count hard links once.
  - On macOS, skip `/System/Volumes/Data` firmlink duplicates when scanning `/`.
- Unreadable folders are counted and listed rather than failing the scan. On macOS a hint about Full Disk Access is shown.
- **Rescan** the whole scan or just the selected folder.

**Views** (all linked to the same selection)
1. **Treemap** (main area): squarified layout, cushion shading, files coloured by extension. Hovering a file highlights it and shows its path and size in the status bar.
2. **Folder tree** (left, in a splitter): sorted by size, with each row showing name, size and percent of parent.
3. **Extension legend** (bottom or right): the top extensions by total size, with colour swatch, total size and file count. Clicking an extension highlights all its files on the map.
4. **Breadcrumb bar** above the map shows the current zoom root. Each segment can be clicked.
5. **Status bar**: the hovered or selected path, its size, the free space on the volume, and an error count.

**Interaction**
- Click selects (and syncs the tree). Double-click a folder zooms in. Backspace, mouse back, or the breadcrumb zooms out.
- Right-click menu:
  - Reveal in Finder / Explorer / file manager
  - Open
  - Copy Path
  - Zoom Here
  - Rescan Folder
  - **Move to Trash…** (confirmed first; uses the `trash` crate, never a permanent delete). The node's size is then subtracted from the tree and the map re-laid out.
- Menu bar (native on macOS through agg-gui-shell):
  - File: Open Folder, Rescan, Quit
  - View: Size Mode, Cushion Shading on/off, Colour By (Extension / Top Folder), Zoom Out
  - Help: About

**Web demo (wasm, GitHub Pages):** the full app running in the browser against a **simulated drive**: a deterministic, realistic synthetic file tree (OS folders, apps, photos, videos, `node_modules`, caches…) generated by `hdtreemap-core::demo_fs`. The "scan" streams that tree at a believable pace, so the progress screen and the live map during the scan are shown too. Every menu, view and action works, with platform actions simulated: Move to Trash removes the node from the model, and Reveal/Open show a toast saying it's a demo. A banner makes clear it is a demo. The start screen offers several descriptive simulated drives, each with its own tree profile:

| Simulated drive | Size / free | What it shows off |
|---|---|---|
| Nearly Full Laptop SSD | 512 GB / 9 GB | Almost out of space: find what's eating it |
| Developer Workstation | 1 TB / 310 GB | Thousands of `node_modules`, `target/` and `.git` folders |
| Photo & Video Library | 2 TB / 640 GB | A few huge video files among many photos |
| Small USB Stick | 32 GB / 11 GB | A small, simple drive and a quick scan |
| Messy Downloads Folder | 256 GB / 70 GB | Duplicates, installers, archives and odd extensions |
| Huge Archive Server | 8 TB / 1.2 TB | Millions of files; stress-tests the treemap |

**Explicitly not in v1:** duplicate finder, reading the MFT or other raw filesystem structures, saved scans or history, network drive tuning, sunburst view.

## 3. Architecture

Repo layout follows Critters and AstroRock (`HDTreeMap/`, a git submodule of rust-apps):

```
HDTreeMap/
  Cargo.toml              workspace; agg-gui / agg-gui-shell from crates.io + [patch] to ../agg-gui
  CLAUDE.md  README.md  CHANGELOG.md  LICENSE
  scripts/pre-commit-check.{sh,ps1}
  .github/workflows/ci.yml        fmt + clippy -D warnings + test on ubuntu/macos/windows
  .github/workflows/release.yml   (M6) zipped binaries + macOS .app
  hdtreemap-core/         rlib — everything testable, no platform code
    src/scan/             walker (jwalk), progress, cancel, inode dedup, fs boundaries
    src/model/            arena tree, ext table, size modes, subtract-on-delete
    src/layout/           squarify + cushion coefficients (pure, no drawing)
    src/render/           cushion rasteriser → RGBA buffer, palette
    src/ui/               widgets: TreemapView, FolderTree, ExtLegend, Breadcrumb, StatusBar, StartScreen
    src/platform.rs       trait PlatformServices { pick_folder, reveal, open, trash }
  hdtreemap-native/       tiny bin: ShellConfig + agg_gui_shell::run, implements PlatformServices
  hdtreemap-wasm/         cdylib: web shell + DemoPlatform (simulated services) + demo_fs source
  demo/                   static page / bun bundle for GitHub Pages (like Critters/demo)
```

Scanning is behind a `ScanSource` abstraction: `FsScanner` (native only, `cfg(not(wasm32))`, uses jwalk/rayon) and `DemoScanner` (all targets, synthetic tree, time-sliced so it works single-threaded on wasm). Both feed the same incremental tree-builder so the UI can't tell them apart. Rayon-parallel rasterisation is native-only; wasm rasterises serially.

### 3.1 Data model (`model/`)
- **Arena tree**: `Vec<Node>` indexed by `u32`. Each node holds `parent`, `first_child`, `next_sibling`, a name index (all names in one `String` slab), `alloc_size: u64`, `apparent_size: u64`, `file_count: u32`, an extension id (`u16`), and flags (dir, error, link, etc.). That is about 40 bytes per node, so 5 million files fit in roughly 200 MB.
- Children are sorted by the active size, descending, after the scan finishes (and again when the size mode changes).
- `ExtTable`: extension id → name, total bytes, count, colour. Built from the finished tree.
- *As built (M1):* `Node` is exactly 40 bytes (a test pins it): the name has no length field
  because names are appended to the slab in node order, so a name ends where the next
  node's begins. Directory sizes are subtree totals of their files (a directory's own blocks
  are not counted). `remove_subtree` unlinks and flags the subtree and subtracts it from
  every ancestor. "Largest folders" skips wrapper folders whose biggest subfolder holds
  ≥ 90% of them, so a chain like `Users → me → Library` lists the folder that matters.

### 3.2 Scanner (`scan/`)
- `jwalk` with a rayon pool, `follow_links(false)`.
- `process_read_dir` filters out entries on other devices and drops hard-link duplicates using a `(dev, ino)` set.
- Allocated size:
  - Unix: `st_blocks * 512`.
  - Windows: `GetCompressedFileSizeW` via `windows-sys` (falling back to the cluster-rounded apparent size). Reparse points are skipped.
- The scan runs on a worker thread. The worker:
  - publishes progress through atomics (counts, bytes) and a `Mutex<String>` (current path);
  - calls `UiQueue::signal_async_state_change()` at most about every 100 ms;
  - sends the finished arena back over a channel.
- Cancel is an `AtomicBool` the walker checks.
- *As built (M1):* the platform picks the source (`PlatformServices::scan_source`). The UI
  polls it once per frame from an agg-gui `ui_thread` drain hook (`state/pump.rs`) with an
  8 ms budget; `DemoScanner` generates its chunk in that slice (paced to a believable
  1.5–20 s per drive), `FsScanner` only checks its channel. Hard links are de-duplicated on
  Unix only; Windows junctions and mount points are not followed because std reports them
  as symlinks. Names are stored as UTF-8 (lossy for non-UTF-8 names).
- **Design choice:** v1 shows a progress screen and then the full map, which keeps the model simple. Showing the map live while scanning (as SpaceSniffer does) is a stretch goal; the arena design doesn't rule it out.
  *Superseded (M5): the map is live during the scan; see the as-built notes below.*
- *As built (M5), the live map:* the walk (`scan/walk.rs`) turns entries into records; an
  `Assembler` (`scan/assemble.rs`) builds the tree from them. `FsScanner` sends records
  from its worker in batches (4,096 or 50 ms) over a channel and applies them in `poll` on
  the UI thread, so the UI owns the one growing tree and lays it out with no locks or
  copies (`ScanSource::partial`); `scan_blocking` applies them inline. Both sources keep
  per-extension totals as files arrive and sort the finished tree a time slice per poll.
  `AppState::with_result` hands views a `ScanView` (live or finished), so every view works
  on the partial tree unchanged; a **live tick** (`state/live.rs`) bumps the tree version
  at most every 400 ms, longer if the refresh (extension totals, layout, raster, rows)
  would take over 30% of the interval. A tick's frame skips the scan's own step, and the
  map rasterises a tick's layout on the next frame. The results view replaces the scan
  screen: a scan strip shows the counters and Cancel; Rescan and Move to Trash wait; at
  the end the screen becomes `Results` without a rebuild, keeping zoom and selection.
  Measured on `~/Development` (1.05 M files, 10-core Apple Silicon, load 6-7): live
  8.6-8.8 s vs blocking 8.3-8.5 s (+3-4%), refresh 20-23 ms mean, longest frame 36-42 ms
  at 2400×1500. Web demo, archive server (1.56 M files) in headless Chrome at 1600×1000:
  paced scan 18.2 s, frames p50 16.7 ms, p99 33 ms, longest 33-50 ms (was 133 ms before
  the slicing), at most one task over 50 ms.
- *As built (M5), macOS metadata:* a folder's entries come from one `getattrlistbulk`
  (`scan/apfs.rs`) instead of an `lstat` each; mount points, firmlinks and entries with
  errors still use `lstat`. Files with `EF_MAY_SHARE_BLOCKS` get one `getattrlist` for
  `ATTR_CMNEXT_CLONEID` and `ATTR_CMNEXT_PRIVATESIZE`, and a clone family is counted once
  (first member in full, others at their private size), like hard links. Asking the bulk
  read for those two for every entry doubled the system time, so it doesn't.
- *As built (M5), whole-disk speed:* `/` on this Mac (2.81 M files, 1.02 M folders,
  load 7-9): 37 s, both M4 and M5; M4's earlier 19.5 min was a cold cache under very
  heavy load. 1.0 M of those entries (600 k folders) are one temp folder of test
  output, which alone takes 23-25 s and is disk-bound: `du` needs 38 s for it at 44%
  CPU, and the kernel's vnode cache (263 k) is far smaller than the disk, so every
  whole-disk scan is cold. Sampling shows jwalk's pool threads mostly waiting on the
  mutex of rayon's `par_bridge`; reading big folders in parallel chunks was tried and
  was slower (reverted). A walker without jwalk's ordered queue might gain more; see §5.
  Nothing on the disk needed skipping: `.Spotlight-V100` and `/private/var/vm` are
  counted (by size), `/dev` is another device, and no file is ever opened.

### 3.3 Layout (`layout/`)
- Squarified layout from the zoom root down to the visible pixel size. Recursion stops when a rectangle is smaller than about 1 px², and the leftover area is drawn as one aggregated block.
- Output is a flat `Vec<LayoutRect { node, rect, cushion: [f32; 4] }>`, the cushion surface coefficients accumulated as in the van Wijk paper. The same list is used for hit testing (point → deepest rectangle, by walking the tree's rectangles).
- This is pure code that takes a tree and a rectangle and returns rectangles, so it is easy to unit-test (areas add up, nothing overlaps, everything stays in bounds, aspect ratios are sensible).
- *As built (M2):* coordinates are physical pixels, Y down (the raster's layout). The list is
  pre-order (a folder before its contents) and each rectangle has a kind: `Dir` (tiled by
  its children, not painted), `File`, `FolderBlock` (a folder none of whose contents is
  ≥ `min_area`, default 1 px²) or `Aggregate` (one per folder: the children below
  `min_area`, with their count and bytes). Painted rectangles tile the bounds exactly; a
  pixel belongs to the rectangle containing its centre. Cushion: ridge height 0.4 at the
  zoom root, ×0.75 per level, coefficients `[a, b, c, d]` of `a·x² + b·y² + c·x + d·y` as in
  WinDirStat's `AddRidge`. Hit testing uses a 32 px cell grid; each rectangle stores its
  parent's index for the folder chain. No gaps between folders: the cushions show nesting.

### 3.4 Rendering (`render/`)
- Cushion shading is computed per pixel, so it is not a vector-fill job. The map is rasterised straight into an RGBA buffer the size of the widget in physical pixels: for each file rectangle, every pixel gets `ambient + diffuse·max(0, n·L)`, with the normal taken from that rectangle's cushion coefficients. Bands of rows are split across rayon.
- The buffer is drawn with `draw_image_rgba_arc` (the texture is cached by `Arc` pointer). It is only re-rasterised when the size, zoom root, size mode, colour mode or tree changes.
- Hover and selection outlines and the extension highlight are drawn on top as vector strokes in `paint_overlay`, so moving the mouse never re-rasterises the map.
- Palette: 12–16 hand-picked distinct hues for the top extensions and neutral grey for the rest, the same idea as WinDirStat.
- *As built (M5):* **Colour By** top-level folder gives the zoom root's 16 biggest
  children a hue each, shared by everything inside them (blocks at 70% brightness), grey
  for the rest; the palette is cached per tree version, scheme and (by folder) zoom root,
  and switching only re-rasterises. The extension highlight dims on top of either scheme.
  The legend lists the top folders in that mode.
- Performance target: under 10 ms per frame when nothing has changed (agg-gui rule), and under about 150 ms to re-rasterise a 4K map with a million files. Both are measured with a stats env var, following the `CRITTERS_STATS` pattern.
- *As built (M2):* `I = Ia + max(0, Is·n·L)` with `Ia = 0.15`, `Is = 1 − Ia`, `L` ∝ (−1, −1, 10),
  times a 1.2 brightness gain, clamped. Flat mode darkens each rectangle's right and bottom
  pixel line. Rows go in 16-row bands (rayon natively, serial on wasm). `HDTREEMAP_STATS=1`
  prints each layout and raster pass and, once a second, the CPU layout+paint time per
  frame; `examples/bench_treemap` times them headless. Measured on a loaded 10-core Apple
  Silicon machine, archive-server demo (1.56 M files) at 3840×2160: layout 45–90 ms, raster
  13–25 ms; hovering it in a 2400×1442 window: 0.85 ms average frame (CPU).
- *As built (M2):* zoom root, hover, selection and shading live in `AppState`
  (`state/view.rs`) with three versions widgets key on: `tree_version` (new scan, size
  mode), `map_version` (+ zoom, shading; the breadcrumb), `detail_version` (+ hover,
  selection; the status bar). Switching the size mode no longer rebuilds the screen.

### 3.5 UI widgets (`ui/`)
These are built from existing agg-gui widgets wherever possible:

| Piece | agg-gui building blocks |
|---|---|
| Overall layout | `FlexColumn` (menu, breadcrumb, `Splitter`, status bar) |
| Folder tree | `TreeView` with the size and percent drawn in the row label. If it can't show columns cleanly, add that to agg-gui rather than working around it locally. |
| Extension legend | `Table` (virtualised, sortable through `HeaderClick`) |
| Treemap | Custom `TreemapView` widget (paint, `on_event`, `tooltip_text`) |
| Context menu | `PopupMenu` |
| Menu bar | `MenuBar` / native `MenuBarModel` |
| Start screen | `Button`s, `Label`s and `ProgressBar` per volume |
| Scan progress | `ProgressBar` (indeterminate), `Label`s, Cancel `Button` |
| Confirm trash | `ModalSheet` |

All icons are Font Awesome code points, per the agg-gui rules.

*As built (M3):* the middle of the results view is a horizontal `Splitter` (28% for the
left column, ratio kept in `AppState` for the session). The left column is a vertical
`Splitter`: the folder tree above the legend (60/40). The map keeps the full height, and
the two lists read as one sidebar.
- **Folder tree** (`ui/folder_tree/`): a `FolderTree` wrapper owns the `TreeView` and syncs
  it with `AppState` once per layout, both ways. A map selection opens the path, selects
  the row and scrolls to it; a row selection or hover drives the map; a double click or
  Enter on a folder zooms. `TreeView` has no column support, so the row label carries
  `name · size · % of parent`; there is no right-aligned bar. Its icon slot takes no
  glyph, so the Font Awesome folder and file glyphs are drawn once into `IconImage`s. It
  also has no select, scroll or change-callback API, and its rows' labels take a click's
  focus target. So the wrapper writes its node list, scrolls it with a wheel event, and
  claims the pointer and focus, forwarding events to it.
- **Extension legend** (`ui/ext_legend.rs`): an agg-gui `Table`. A rows provider refreshes
  from `AppState::zoom_extensions` (`ExtTable::from_subtree`, cached per zoom root). A cell
  painter draws the swatch from the shared `AppState::palette`. `HeaderClick` sorts.
- **Highlight**: the map is drawn from a cached raster painted with
  `Palette::highlighting` (every other colour dimmed). Outlining each file in the overlay
  was measured first: about 9 ms a frame for 2,105 `.jpg` rectangles on the archive
  server. The dimmed raster costs 1.4–6.5 ms once per change and nothing per frame after
  that.
- **Measured** (`examples/bench_views`, archive server, 1600×1000, agg-gui's software
  renderer, so upper bounds; Apple Silicon under heavy load):
  - idle 6.6 ms, hovering the map 7.0 ms, hovering tree rows 6.7 ms, hovering with
    `.jpg` highlighted 7.2 ms;
  - selecting on the map 12.4 ms mean (layout 0.7 ms; the rest is the software renderer
    rasterising the rebuilt tree rows' labels).
  - Native shell (GPU), `HDTREEMAP_STATS`, archive server with `.jpg` highlighted, about
    1720×1440 px map: 1.25 ms average CPU layout+paint per frame.

*As built (M5):* settings (`settings.rs`) are one JSON blob of size mode, shading, colour
scheme, splitter ratios and the five most recent scan targets: natively
`<config dir>/HDTreeMap/settings.json` (and `window.json` through agg-gui-shell's
`WindowBoundsStore`), on the web `localStorage` through agg-gui-web-shell's
`LocalStorageSettings`. AppState writes it from the shells' idle hooks through agg-gui's
`AutoSave` (on change, never mid-drag; flushed on exit or page hide); unknown or broken
values fall back to defaults. The start screen lists the recent scans. The folder tree's
root row shows the drive or folder name, the full path as its tooltip.

*As built (after v0.1.0):* a light theme by default, with dark and Match System
(`theme.rs`, `state/theme.rs`), chosen from View ▸ Theme or the toolbar's sun/moon button
and remembered in the settings blob (`"theme"`; missing or unknown means light, so
v0.1.0 blobs start light). It switches live: most widgets paint with agg-gui's current
`Visuals`; the few built with a theme colour rebuild on `AppState::theme_version`; the
folder tree recolours its icons in place. The cushion hues are the same in both looks;
folder-block grey and the empty background follow the look (so the map re-rasterises on a
flip), and the hover / selection / folder outlines carry a contrasting inner line. Match
System reads winit's `Window::theme` natively (macOS and Windows; X11 and Wayland report
nothing, so light) and `prefers-color-scheme` on the web (watched with `matchMedia`); the
demo page's background follows the remembered theme before the wasm loads.

*As built (M4):* the root is a `Stack`: the menu bar (unless the shell installed the
macOS system one) over the screen, then the overlays: a `ContextMenuHost` that opens an
agg-gui `PopupMenu` for `AppState::request_context_menu` (from the map and the tree), the
toasts, and the Move to Trash and About `ModalSheet`s. (*M6:* the toasts moved onto
agg-gui's `ToastHost` / `Toasts`, which wraps the whole root; `ui/toast.rs` is gone.) The menus are described once as data (`ui/menus.rs`) and turned into the
in-window `MenuBar`, the macOS `MenuBarModel` (in `hdtreemap-native`) and the shortcut
table; `ui/commands.rs` runs, enables and checks every command, `ui/node_actions.rs`
the per-item ones. Move to Trash calls `PlatformServices::trash`, then
`AppState::remove_node`; Rescan Folder runs a `ScanSource` for the folder in the
background (the demo regenerates the whole drive) and `Tree::replace_subtree` splices it
in. Items whose stored name is lossy (`NodeFlags::LOSSY_NAME`) are refused by Reveal,
Open, Rescan and Trash. The folder tree runs on agg-gui's TreeView events and selection
API; folders it opened for an earlier selection are closed and their rows dropped when
the next one is shown. Measured (`bench_views`, archive server, software renderer):
idle 6.5 ms, hover 6.8 ms, select on the map 8.7 ms (was 12.4 ms).

### 3.6 Platform services (native crate)

| Service | macOS | Windows | Linux |
|---|---|---|---|
| Pick folder | `rfd` | `rfd` | `rfd` |
| Reveal | `open -R <path>` | `explorer /select,<path>` | `dbus-send` to FileManager1 `ShowItems`, falling back to `xdg-open <parent>` |
| Open | `opener` crate | `opener` crate | `opener` crate |
| Trash | `trash` crate | `trash` crate | `trash` crate |
| Volumes | `sysinfo::Disks` (filtering out pseudo-filesystems on Linux) | `sysinfo::Disks` | `sysinfo::Disks` |
| Open URL | `opener::open_browser` | same | same |

*As built (M4):* the scan root is canonicalised first. Linux decides mount handling from
`/proc/self/mountinfo` (`platform/mountinfo.rs`): mounts of other filesystems and mounts
repeating folders the scan reaches anyway (bind mounts) are skipped, btrfs subvolumes of
the root's filesystem entered; the volume list merges only mounts of the same root. macOS
`/` skips only the firmlinked folders of `/System/Volumes/Data` (`/usr/share/firmlinks`).
Windows: `\\?\` prefix for long paths in `GetCompressedFileSizeW`, `explorer
/select,"<path>"` as a raw argument; hard links are not de-duplicated (that needs a handle
per file; see the README's known limitations). APFS clones are counted at each copy.

## 4. Milestones

Each milestone ends green: fmt, clippy `-D warnings` and tests.

1. **M0 – Scaffold**: workspace (core / native / wasm), CLAUDE.md (copied from the Critters rules), MIT LICENSE, pre-commit scripts, CI matrix on all three OSes plus a wasm check and Pages deploy, and the start screen running both natively (real volumes) and in the browser (simulated drive).
2. **M1 – Scanner + model** *(done)*: jwalk scan into the arena, both size modes, inode dedup, filesystem boundaries, cancel, and error collection. Tests use temporary directory trees (including hard links and symlinks, on Unix). Includes a CLI-ish `--dump-top N` debug flag for checking the scanner without the UI.
3. **M2 – Treemap** *(done)*: squarify, cushion rasteriser, `TreemapView` with hover and status bar, progress screen, and zoom in and out with the breadcrumb. Unit tests for layout invariants and a golden-image test for the rasteriser.
4. **M3 – Linked views** *(done)*: folder tree and extension legend, all synced with the map selection, plus highlight-by-extension.
5. **M4 – Actions** *(done)*: context menu, reveal, open, copy path, rescan folder, Move to Trash with confirmation, and the menu bar items.
6. **M5 – Polish and perf** *(done)*: measure on a real full-disk scan of each OS, **live map during the scan**, remembered window bounds and settings, and the colour-by-top-folder mode. *As built:* live map, APFS clone accounting and bulk metadata (§3.2), colour by top-level folder (§3.4), settings and Recent (§3.5); measured on macOS only (Linux and Windows full-disk runs are still to do).
7. **M6 – Ship** *(done)*: README with a hero screenshot, a GitHub release workflow (zipped binaries for all three OSes, a macOS `.app` via `cargo-bundle`), and the rust-apps README entry and submodule. *As built:* `release.yml` builds Linux (tar.gz), Windows (zip, icon set with rcedit) and a universal macOS `.app` assembled by `scripts/package-macos.sh` (lipo, an `Info.plist` template, ad-hoc signature; no `cargo-bundle`), on a `v*` tag or by hand; the app icon is drawn by the app's own renderer (`icon.rs`, `examples/make_icons`). Toasts moved to agg-gui's `ToastHost`; the demo generator interleaves top-level folders so the live map shows a mix early. The rust-apps README entry is left to the superproject.

## 5. Risks and open questions
- **Million-node trees in `TreeView`**: it must be lazy, expanding only on demand. Check this early in M3.
  *Resolved (M3):* rows are added on expansion, capped at 200 per folder, and folders the
  tree opened for an earlier selection are closed and their rows pruned (`TreeView`'s
  layout cost grows with every row it holds). The archive server's 1.56 M files start
  with under 20 rows; clicking around the map keeps it near 700.
- **macOS privacy**: without Full Disk Access, `~/Library` and similar folders return permission errors. We report them clearly; we don't try to get around them.
- **Windows sizes**: allocated size for compressed, sparse or OneDrive placeholder files varies. Use `GetCompressedFileSizeW` and document the behaviour.
- **Scanning speed vs WizTree**: we accept the speed of a parallel walk. Reading the MFT is a possible v2 item.
  *M5:* on macOS a whole disk is disk-bound in its biggest trees (§3.2 as-built notes).
  jwalk hands out directory reads through one mutex (rayon `par_bridge`), which is where
  its threads wait on wide trees of small folders; a walker of our own (rayon scope per
  folder, records keyed by folder token instead of depth order) is the next thing to try
  if whole-disk speed matters more.
- **wasm is single-threaded**: the demo scan and the rasteriser must be time-sliced or fast enough serially.

## 6. Open items after v0.1.0

- **A walker of our own** (rayon scope per folder, records keyed by folder token) in place
  of jwalk, whose directory reads funnel through one mutex on wide trees (§5).
- **Hard links on Windows** are counted once per link; de-duplicating them needs a handle
  per file (`GetFileInformationByHandle`), so it wants a cheap way to find the files with
  more than one link first.
- **Full-disk measurements on Linux and Windows** (M5 measured macOS only).
- **Signed and notarized builds**: an Apple Developer ID and notarization for the `.app`,
  Authenticode for the Windows `.exe`; an installer or `.dmg`, and Linux packages
  (AppImage, `.deb`, Flatpak).
- **Sunburst view** and other v2 ideas from §2's "not in v1" list: duplicate finder,
  reading the MFT, saved scans, network-drive tuning.
- **Publishing to crates.io** (the crates carry the metadata; agg-gui-web-shell must be
  published first).
